# Запуск Project Iz на Linux-сервере

Это подготовленные настройки для отдельного сервера. Они не запускают и не меняют действующую установку Windows. Полный запуск и восстановление данных проверяются на сервере до допуска сотрудников.

## Схема

Один сервер x86-64 с 4 vCPU, 8 ГБ RAM и диском 75–80 ГБ: Next.js, PostgreSQL 17, MinIO, ClamAV, worker, Telegram-получатель и Caddy. Для старта с тремя сотрудниками и 10 ГБ документов это рабочая оценка; расход памяти и диска нужно измерить после переноса. Ubuntu 24.04 LTS, Docker Engine и Compose plugin устанавливаются из официальных репозиториев.

Снаружи доступны HTTPS и перенаправление HTTP. PostgreSQL, MinIO, его консоль и ClamAV не публикуют порты сервера. Caddy передаёт запросы приложению; прямой раздачи файлов MinIO нет. Существующая проверка сотрудника, прав и статуса антивирусной проверки сохраняется.

## До запуска

1. Создать сервер, ограничить SSH своим доступом по ключу, разрешить входящие TCP 80/443. Проверить правила IPv4 и IPv6 в сетевом экране провайдера.
2. Получить приватный репозиторий в `/opt/project-iz` с правом чтения. Секреты хранятся отдельно от Git; персональный GitHub-токен не записывается в URL репозитория.
3. Направить DNS A домена на IPv4 сервера. AAAA добавляется только при настроенном IPv6. Существующий домен компании можно использовать с поддоменом `crm`.
4. На сервере скопировать `deploy/production.env.example` в `.env`, заполнить адреса и секреты, установить права `chmod 600 .env`. Не копировать шаблон поверх локального `.env` Windows. Пароль PostgreSQL — случайные 64 шестнадцатеричных символа: `openssl rand -hex 32`. Такой пароль безопасен внутри URL подключения. Не сохранять вывод с секретами в Git или общедоступных журналах.
5. Подключить SMTP, подтвердить отправляющий домен через DNS провайдера почты, проверить отправку приглашения и восстановление пароля. Пример настроен на Resend, порт 2587.
6. Согласовать внешнее хранилище зашифрованных резервных копий и расписание. Копии провайдера сервера дополняют резервирование базы и документов.

Все следующие команды выполняются **только на Linux-сервере** из `/opt/project-iz`. Для краткости используется функция:

```sh
dc() { docker compose --env-file .env -f compose.production.yaml "$@"; }
dc --profile telegram config --quiet
dc build
dc up -d db storage scanner
```

Команда `config --quiet` проверяет настройки без печати секретов. Шаблоны `REPLACE_WITH` должны быть заменены до запуска; проверка синтаксиса не проверяет качество паролей.

## Перенос действующих данных

До запуска web, worker и telegram нужно восстановить существующую базу и документы. Новую пустую CRM поверх переноса не инициализировать вручную созданием сотрудников.

1. Снять предварительную копию и выполнить пробное восстановление отдельно. Сверить клиентов, дела, сотрудников, бухгалтерию и документы.
2. В согласованное время закрыть локальный доступ и остановить web, worker и Telegram-получатель Windows. Оставить PostgreSQL и MinIO работающими для финального копирования. Получить согласованный финальный дамп PostgreSQL и экспорт объектов. Зафиксировать время среза и контрольные суммы.
3. Восстановить дамп PostgreSQL в пустую базу сервера. Перенести все объекты приватного bucket с исходными ключами, включая файлы старых версий документов. Каждая версия CRM хранит отдельный `storage_key`; скачивание использует именно этот ключ. Перенос только последних версий документов оставит старые записи без файлов. Сверить ключи, размеры и контрольные суммы с базой. Если нужно сохранить внутреннюю историю версионирования самого MinIO, отдельно проверить способ её переноса на копии.
4. Не копировать Windows-каталог PostgreSQL прямо в Linux. База переносится через pg_dump/pg_restore. Не считать GitHub копией базы или документов.
5. Проверить восстановление и только затем применить миграции и запустить приложение:

```sh
dc run --rm --no-deps initialize
dc up -d --no-deps web worker proxy
```

Сертификат HTTPS выдаётся Caddy после готовности DNS и доступности портов 80/443. Сохранённые учётные записи берутся из восстановленной базы.

Проверить вход каждого уровня доступа, отсутствие доступа без входа, скачивание старой и новой версии документа, загрузку и проверку антивирусом, сохранение бухгалтерской операции, чаты, отправку письма и фоновое напоминание. Healthcheck должен показывать `ready: true`; HTTP 200 сам по себе не подтверждает готовность.

Для Telegram сохранить прежний токен в серверном `.env` после остановки локального получателя. Проверить отсутствие действующего webhook; script намеренно откажется работать при его наличии. Затем:

```sh
dc --profile telegram up -d --no-deps telegram
```

Не запускать два получателя одного бота с разными базами одновременно. После переключения сотрудники работают на домене, а локальную установку используют только для разработки с отдельными данными и ботом.

## Последующие обновления

Сначала проверить код локально, сохранить commit и отправить его на GitHub. До обновления сервера сделать проверенную согласованную резервную копию. Обновление требует короткого окна недоступности; время сборки измеряется при первом запуске.

```sh
git pull --ff-only
dc --profile telegram stop web worker telegram scanner
dc build
dc run --rm --no-deps initialize
dc up -d --no-deps scanner web worker proxy
# Выполнить только если Telegram был настроен и включён:
dc --profile telegram up -d --no-deps telegram
dc ps
```

При ошибке сборки или миграции не запускать частично обновлённую систему. Сохранить диагностику без секретов и восстановить согласованную рабочую версию. Откат кода не отменяет изменения схемы базы.

## Резервные копии и обслуживание

Ежедневно: согласованная копия PostgreSQL и всех объектов приватного bucket, шифрование перед отправкой во внешнее хранилище, хранение 30 дней и оповещение при сбое. Для небольшого объёма можно останавливать web, worker и telegram на время среза. Копия должна включать каждый `storage_key`, указанный в базе, и остальные используемые объекты, включая шаблоны договоров. Внутренняя история MinIO резервируется отдельно при необходимости. Шифровальный ключ хранить отдельно с возможностью восстановления.

Проверить восстановление на отдельном сервере до допуска сотрудников и повторять проверку ежемесячно. Автоматическое внешнее резервирование пока не установлено: нужны учётная запись хранилища и проверенный способ копирования MinIO. Возможная потеря данных при ежедневных копиях — до 24 часов.

Контролировать память, свободный диск, состояние служб и успешность копий; расширять диск до его заполнения. Обновлять ОС, Docker и образы после проверки. Имена томов стабильны благодаря имени проекта `project-iz-production`; команды удаления томов для рабочей CRM не применять.
